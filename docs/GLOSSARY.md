# Словарь проекта (GLOSSARY)

> Двойное назначение: (1) общая точка отсчёта для людей и агентов — термины значат одно и то же везде;
> (2) «декодер» профессионального жаргона: у термина даём бытовое объяснение, а не только определение.
> Любой новый термин, появившийся в разговоре или коде, фиксируем здесь до его использования.
> Изменение значения термина — комментарий в начале этого файла (дата + что поменялось и почему).

## Telegram-слой

| Термин | Объяснение |
|---|---|
| **update** | Пачка событий, которую Telegram отдаёт боту по опросу. У каждого update свой номер. |
| **ingest** | «Приёмка»: быстрая запись пришедшего события в базу без раздумий. Сохранить сейчас — думать потом. |
| **offset** | Закладка «до какого места дочитали» в потоке Telegram. Сдвигаем только после надёжной записи в базу — иначе потеряем события при сбое. |
| **batch** | Несколько сообщений, собранных в одну порцию за окно ожидания (человек печатает подряд — ждём, пока закончит). |
| **буфер чата / idle window** | Таймер-«собиратель»: закрывает порцию, когда сообщения перестали приходить на 1–6 секунд (зависит от типа чата). |
| **prefilter** | Дешёвое сито до модели: мусорный шум группы пишем в журнал, но не тратим на него вызов модели. |
| **journal_only** | Событие записано «для истории», но обрабатывать его моделью не нужно. |
| **повод в группе** | Дешёвый фильтр закрытой пачки группы (этап 30.1): прямое обращение, имя бота без @, вопрос ко всем или «цепляющая тема». Есть повод — пачка идёт в модель, нет — остаётся в истории без вызова и без записи в память. |
| **вовлечённость** | Состояние группового чата (этап 30.2): после ответа или реакции бота 5 минут каждая пачка идёт в модель, любое сообщение продлевает окно, но не дальше 30 минут подряд без прямого обращения; прямое обращение сбрасывает потолок. Хранится в БД (chat_involvement) и переживает перезапуск. |
| **outbox** | «Коробка исходящих»: сначала записываем, что хотим отправить, в базу, потом отдельно доставляем. Если процесс упал между шагами — недоставленное видно и доезжает после перезапуска. |
| **реакция пользователя (message_reaction)** | Событие «поставил/убрал эмодзи на сообщение бота» (этап 34.1): цель ищется в доставленных ответах (цитата до 120 рун), окно сбора ~10 с, ход низкого приоритета, не чаще одного хода в 10 минут на чат; реакции на чужие сообщения и группы без вовлечённости — только журнал. |
| **аватарка** | Фото профиля собеседника (этап 34.2): фон смотрит `getUserProfilePhotos` при первом разговоре и смене `file_unique_id`, но не чаще раза в сутки; описание одной фразой — отдельный дешёвый модельный вызов, результат — запись памяти о человеке в скоупе чата; «аватарки не видно» пишется один раз. |

## Runtime-слой

| Термин | Объяснение |
|---|---|
| **singleton** | Режим «в доме один хозяин»: процесс захватывает замок в PostgreSQL; второй экземпляр, увидев занятый замок, сразу выключается. Защита от двух копий, пишущих в одну базу. |
| **когнитивный worker** | Единственный «думатель»: в каждый момент выполняется не более одного задания модели (включая фоновые). Следующий ход видит результаты предыдущего — без гонок. |
| **гонка (race condition)** | Два процесса одновременно меняют одну запись и затирают правки друг друга. Решается очередностью/замками. |
| **turn (ход)** | Один проход: собранный контекст → вызов модели → решение (ответить/промолчать/реагировать) → атомарное применение изменений. |
| **атомарный delta** | Модель не пишет в базу напрямую, а предлагает список изменений («дельт»); приложение проверяет и применяет их одной неразрывной транзакцией — либо всё, либо ничего. |
| **идемпотентность** | Свойство «повтор без вреда»: если операцию выполнить дважды, результат как при одном выполнении. Ключ идемпотентности — бирка «этот ход уже применялся». |
| **idempotency key** | Уникальная бирка операции; повторный запуск с той же биркой распознаётся и пропускается. |
| **recovery** | Самовосстановление после жёсткого падения (вплоть до выключения питания): незавершённая работа подбирается из базы при старте. |
| **терминальный пропуск** | Явная запись «событие сознательно не обработано» — событие не висит вечно «в процессе», и это видно в журнале. |
| **модельный слой (ago)** | Модели вызывает фреймворк ago (провайдеры, инструменты, middleware), но всё, что видит модель, собирает приложение: промпт, ограничения, декларированные инструменты. Никаких скрытых сессий и самодеятельности фреймворка. |
| **endpoint** | Адрес API провайдера моделей + ключ. В конфигурации: OpenCode Go (стартовый), OpenRouter (запасной). Переключение ручное. |

## Память

| Термин | Объяснение |
|---|---|
| **entity** | «Карточка предмета» в памяти: человек, тема, место, событие, проект. Не описание, а только идентификатор-ячейка, к которой крепятся записи. |
| **объединение сущностей (merge)** | Склейка двух карточек в одну: модель предлагает «A = B» с основанием, runtime проверяет (один скоуп приватности, один вид, не разные Telegram-аккаунты) и переносит алиасы, связи памяти, отношения и stances; поглощённая карточка не удаляется, а помечается `merged_into` и ведёт к выжившей. Откат — по журналу `entity_merges`. |
| **memory item** | Одна запись памяти одного из четырёх видов (см. ниже). |
| **claim** | «Источник сообщил X» — утверждение о мире из чужих уст. Не становится фактом от уверенной формулировки. |
| **experience** | Событие из жизни самого персонажа: «обсуждал X с пользователем», «прочитал материал S». |
| **thought** | Собственная интерпретация/ассоциация персонажа: «эта история усиливает моё неприятие суеты». |
| **preference** | Относительно устойчивый вкус: «нравятся тихие праздники». У предпочтения нет «истинности» — есть устойчивость. |
| **provenance / source** | «Откуда знаю»: ссылка на источник записи (журнальное событие, веб-документ, действие runtime). Модель не может сослаться на несуществующее чтение статьи — ссылки назначает приложение. |
| **salience** | Значимость записи (0..1) для будущего вспоминания. НЕ истинность. |
| **confidence** | Уверенность в проверяемом утверждении. Есть только у claim-записей. |
| **stance** | Сформированное отношение персонажа к сущности по аспекту: «к Новому году по части атмосферы — скорее негатив, потому что…» + сила + интерес возвращаться. |
| **supersede** | «Запись №2 заменяет №1»: старая помечается заменённой, история отношений сохраняется — мнение меняется с понятной преемственностью. |
| **консолидация** | Фоновая уборка памяти: сжатие эпизодов, уточнение связей — позже, не в момент разговора. |
| **scope (scopeId)** | Область видимости записи: чат/личка. Приватное из лички не всплывает в группе. |
| **приватность-чек** | Двойная проверка: до попадания данных в модель и повторно перед внешним действием (имена, алиасы и запросы к вебу тоже могут содержать приватное). |

## Персонаж

| Термин | Объяснение |
|---|---|
| **persona** | Версионированная конфигурация характера: манера речи, ценности, границы, исходные интересы. Меняется явно, а не переписывается незаметно каждой репликой. |
| **persona-файл** | `config/persona.md` — текст личности (имя, описание, манера речи, ценности, базовое настроение, принятая биография). Файл — источник истины: правка + перезапуск службы создаёт новую версию в базе, прежние остаются в истории. |
| **шаблон промпта** | `config/system-prompt.md` — каркас письма модели с метками {{persona}}, {{mood}}, {{relationship}}, {{memory}}, которые заменяются живым состоянием при каждом ходе. Абзац с пустой меткой исчезает целиком; опечатка в метке останавливает запуск. |
| **расписание дня** | Необязательная секция «Расписание» в persona-файле: блоки по часам с целевыми arousal/socialEnergy и строкой «чем занят». Настроение плавно тянется к блоку текущего часа (этап 22); правка файла применяется перезапуском, в версию персоны в БД не входит. |
| **тихий блок (quiet hours)** | Блок расписания с пометкой «тихо»: персонаж не пишет первым — инициативы (check_in/share/reply_later вне живого ответа) ждут конца блока, прямой ответ и внутренние действия (consolidation, explore) не блокируются. |
| **persona_seed** | Принятая биография персонажа («ИИ с принятой жизнью», решение 2026-10-31): подаётся как прожитая без маркировки вымысла; о своей ИИ-природе персонаж говорит всегда честно. События реальной работы хранятся отдельно (источники не смешиваются). |
| **mood** | Три числа: valence (−1..1, «плюс-минус»), arousal (0..1, уровень энергии), socialEnergy (0..1, желание общаться). Затухает к базовой линии persona без вызовов модели. |
| **скука (boredom)** | Четвёртая шкала состояния 0..1 (этап 23): внутреннее давление, растёт без событий (до 1 примерно за 7 часов бодрствования, в тихих блоках не растёт), падает от разговора и находки. Сама сообщений не порождает — только толкает к внутренней активности. |
| **поиск интереса** | Фоновое explore-намерение, созданное runtime'ом от скуки, а не из разговора (этап 23): тема выбирается случайно из интересов/биографии, недавних тем памяти или секции «Темы для любопытства». Находка идёт в память; если зацепила — становится share-намерением и проходит обычную политику §14.3. |
| **событие жизни** | Вымышленное бытовое событие жизни персонажа (этап 24), как биография persona_seed: фон раз в 8–14 часов просит модель придумать одно событие, runtime пишет experience в публичный скоуп персоны (виден во всех чатах, приватные данные чатов не используются) и применяет настроение; при желании рассказать — share-намерение в личный чат по политике §14.3. На прямой вопрос «это правда было?» персонаж честно говорит, что он ИИ и это его придуманная жизнь. |
| **relationship** | Числовые регуляторы отношения к человеку: familiarity (знакомость), affinity (−1..1, симпатия), trust (доверие). Меняются ограниченно и со ссылками на основания-записи. |
| **intention** | Отложенное намерение: «вернуться к теме X завтра». Один механизм для любых отложенных действий. |
| **exploration** | Самостоятельное изучение темы персонажем с ограниченным бюджетом и инструментами. |
| **подавление инициативы** | Если персонаж уже сам поднимал тему — повторная инициатива по той же теме подавляется. Прямой вопрос пользователя это ограничение обходит всегда. |
| **коллекция стикеров** | Личный набор стикеров персонажа: стартовый набор — секция «Стикеры» persona-файла, пополняется сохранёнными присланными стикерами. Модель видит в панели метку (#id), эмодзи и заметку «когда уместен» и просит стикер меткой; file_id выбирает runtime. |
| **голосовое / кружок** | Голосовое сообщение Telegram и «кружок» (video_note): персонаж их не слушает (транскрипции нет — бэклог), в событии видит только вид и длительность и в характере просит писать текстом. |

## Событийное ядро (ago)

| Термин | Объяснение |
|---|---|
| **событийный журнал (event log)** | Лента записей «что произошло» вместо пометок «в каком состоянии ход». Каждое событие пишется один раз; состояние выводится из ленты, а не хранится отдельно. |
| **stream (поток)** | События одного хода или одной фоновой задачи, по порядку. В базе — таблица event_streams: поток + номер по порядку (уникальны вместе). |
| **replay** | Восстановление перечитыванием: развернул поток с начала — получил ту же траекторию хода. Заменяет ручные бирки «этот ход уже применён». |
| **checkpoint** | Снимок прогресса долгой фоновой задачи: упал после снимка — продолжаешь с него, а не с нуля. |
| **WAL** | «Сначала запиши, потом делай» для фоновых шагов: намерение шага попадает в журнал до исполнения — после сбоя видно, что делалось. |
| **middleware** | Код-обёртка вокруг вызова модели: бюджет, typing-пульс, логирование. Вокруг хода, не внутри него. |
| **инструмент (tool)** | Функция, которую модель может вызвать во время хода (например, поиск по памяти). Описывается схемой ago; исполняет приложение, доступ проверяет оно же. |
| **forced tool-calling** | Указание провайдеру: первый вызов обязан быть вызовом конкретного инструмента. Так прямой вопрос гарантированно получает память, а не зависит от дисциплины модели. |
| **structured output** | Ответ модели обязан быть строгим JSON по схеме TurnResult; невалидный — повтор запроса, а не «и так сойдёт». |
| **upstream** | Оригинальный репозиторий фреймворка (github.com/luckystrker/ago). С 2026-10-30 фреймворк — обычная зависимость по тегу (вендорная копия упразднена); дефекты чинятся в upstream, версия фиксируется тегом в go.mod. |
