## MAJOR

### M1. Секрет из query endpoint утекает в дамп через поле `Error`
`internal/modebug/transport.go:173-175` (`record`: `rec.Error = err.Error()`),
ср. `internal/modebug/replay.go:129-132` (там та же ошибка затирается).

`record()` аккуратно redact'ит URL (`redactURL`) и режет auth-заголовки, но
текст транспортной ошибки пишется как есть. Ошибка `*url.Error` содержит
полный URL запроса: `Post "https://gw.example/v1?api_key=SECRET": dial tcp:
i/o timeout`. Конфиг с ключом в query — официально поддерживаемый случай
(комментарий в `transport.go:224`, тест `TestTransportRedactsSecretQuery`,
`ensureChatPath` бережно сохраняет query).

Сценарий: `MODEL_ENDPOINT=https://…?api_key=SECRET` + любая транспортная
ошибка (таймаут, DNS, рестарт провайдера) → `turn-<id>-call-<n>.json` содержит
секрет открытым текстом в поле `error`. Файл 0600/0700, но RUNBOOK прямо учит
копировать дампы с VPS и разбирать через `jq` — секрет уедет в support-бандл.
Это дыра в задокументированной гарантии «ключ API не пишется», причём рядом,
в replay, тот же класс ошибок уже redact'ится — непоследовательно.

Фикс: в `record()` прогонять `err.Error()` через ту же замену, что в replay
(`strings.ReplaceAll(msg, rawURL, redactURL(...))`), либо хранить в `Record`
`errorURL` отдельно в redact'ированном виде. Тест: транспортная ошибка при
endpoint с `?api_key=` → в файле нет секрета (зеркало `TestTransportRedactsSecretQuery`).

Подтверждено чтением (ветка `err.Error()` без redact; форма `*url.Error`
стандартна). Существующие тесты redact покрывают только `URL`, не `Error`.

### M2. Детектор брака калечит ответы с кодом: аффиксы `{`/`}`/`":` без контекста
`internal/character/garbage.go:67-69` (списки аффиксов), `:129-138` (проверки
префикса/суффикса всего сообщения).

Любое сообщение, начинающееся или заканчивающееся символами `{ } ": ], }, [,
,: ","`, помечается браком целиком — независимо от содержимого. Проба на ветке
(временный тест, удалён после прогона):

| вход | вердикт |
|---|---|
| `func main() {` | «обрывок JSON в конце: {» |
| `if err != nil {` | «обрывок JSON в конце: {» |
| `x = {a: 1}` | «обрывок JSON в конце: }» |
| `return nil }` | «обрывок JSON в конце: }» |
| `[[1],[2]]` | «ряд JSON-знаков» |
| многострочный сниппет, кончающийся `}` | брак целиком (суффикс проверяется по обрезанному сообщению, переводы строк не спасают) |

Сценарий: владелец спрашивает про код (штатный кейс — «говорит с ботом про
код»), бот отвечает несколькими сообщениями, часть — строки кода. Строки-скобки
уходят в repair с требованием «без обрывков JSON» → либо модель уродует код,
подстраиваясь под фильтр, либо брак остаётся и строки выкидываются
(`dropGarbageMessages`), либо весь ответ из одного кода деградирует в
`ignore`/`react` (путь `FixGarbageMessages` → чистка первого ответа → всё брак
→ `degradeAnswerWithoutText`). Легитимный ответ уничтожается именно в том
кейсе, который задание просило не задевать.

Фикс: проверять аффиксы только на сообщениях без признаков кода/речи —
например, не считать аффиксом ` {`/`}` на конце, если в сообщении есть
буквенные идентификаторы и оно длиннее N символов; либо сначала пробовать
распознать «одна пунктуация/чистый мусор», а аффикс-JSON требовать в сочетании
(скобка + соседний JSON-знак, как уже сделано для имён полей через
`jsonNeighbor`). Минимум — юнит-набор «код из живого разговора» в
`garbage_test.go`, чтобы ужесточения не молчали.

Подтверждено пробой (44 строки, таблица выше) + чтением `FixGarbageMessages`
(`internal/character/garbage.go:283-297`) — при persistent-браке чистка бьёт
по первому ответу, валидные строки кода не восстанавливаются.
