## BLOCKER

### B1. Стоп-кран срабатывает внутри одного блока tool-call'ов — прямой вопрос превращается в голую 🤔
`internal/character/middleware.go:424-446`, `stopCraneRejects = 1` (`middleware.go:347`).

`warnedBefore` читается на входе `OnToolExecution`, а middleware не отличает
«второй вызов того же блока» от «модель проигнорировала подсказку»
(нет `OnLLMCall`, подсказка доставляется только следующим LLM-вызовом).
Второй отклонённый вызов в том же блоке: `warnedBefore=true`, `rejects=2 ≥ 1` →
`crane=true` → `ResponseForce` с телом `craneFallbackResult` (react 🤔).

Сценарий: лимит памяти 2, модель одним блоком заказала 4 `memory_search` →
вызовы 1–2 исполнились, вызов 3 отклонён с подсказкой «ответь текстом сейчас»,
вызов 4 (подсказки модель ещё не видела — она в том же блоке) → кран замыкает
цикл. Пользователь с прямым вопросом получает голую 🤔 вместо ответа.
С var `stopCraneRejects=1` достаточно ДВУХ отклонённых вызовов подряд, а не
«модель дважды проигнорировала none».

Исправление: взводить кран только после промежуточного LLM-вызова (запомнить
счётчик LLM-вызовов в момент `warned`; кран — если после него был новый вызов
модели), либо считать `rejects` только через разные модельные ходы.
Существующие тесты (`stage38_test.go`, `stage39_test.go`) моделируют вызовы
разнесёнными во времени и этот кейс не покрывают.

## MAJOR

### M1. Recovery `image_url` обходит проверку «URL из выдачи хода»
`internal/character/turn.go:277-285`, `internal/character/web.go:383-391`.

`WriteModelOutput` пишется ДО `resolveImage` и сохраняет сырой `result.ImageURL`
независимо от вердикта проверки. Восстановление вызывает
`resolveImage(..., allowed=nil)`, а `nil` означает «проверку пропустить».
Комментарий в `turn.go:282-283` («model_output пишется после неё») ложный —
порядок обратный.

Сценарий: модель вернула `image_url` на URL вне выдачи → при генерации
отклонено с логом, фото в outbox нет. Падение процесса между `model_output`
и `apply` (окно расширено сетевым скачиванием в `resolveImage`) → recovery
качает этот же URL через `FetchImage` и кладёт фото в outbox. Отказ генерации
перевёрнут; выдуманный моделью URL уходит пользователю. Учитывая, что слабая
модель регулярно выдумывает URL, а рестарты (деплой) — обычное дело, окно не
гипотетическое.

Исправление: персистить вердикт проверки (или готовый `OutboxImage`/хеш байтов)
в `model_output`; на recovery восстанавливать сохранённое, а не качать заново
(перепроверка по журналу `tool_result` — второй вариант).

### M2. Отмывка provenance: любой URL из свободного текста страницы становится «выдачей хода»
`internal/character/web.go:192-195` (`urlCandidateRe`), `233-249`
(`collectToolResultURLs`), `302-319` (`webResultMW`).

Коллектор regex'ом собирает URL из ТЕКСТА результата инструмента, а не только
из структурированных полей (список `Images` страницы / ссылки результатов поиска).

Сценарий: страница содержит в теле строку `see https://attacker.example/x.png`
(не `<img>`, просто текст) → адрес попадает в `allowed` → модель ставит его в
`image_url` → `resolveImage` принимает → бот качает и шлёт чужой URL. Текст
страницы (и промпт-инъекция из `web_fetch`/памяти) управляет множеством
разрешённых адресов — проверка «URL из выдачи» аутентифицирует появление
подстроки, а не предложение картинки.

Исправление: для `image_url` принимать только структурированные источники
(`Images` страницы, ссылки результатов поиска); вести два множества (все URL
для панели vs image-URL для `image_url`).
