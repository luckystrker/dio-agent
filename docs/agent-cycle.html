02 · internal/memory

Как устроена память

Единая типизированная память на таблицах миграций 000004_memory и 000007_embeddings: сущности, записи со ссылками на источники, stances и векторный индекс. Доступ фильтруется в SQL до ранжирования — модель физически не видит недоступные записи.

Типы и статусы — как в коде

Виды записей (item.go:16) и их жизненный цикл:

claim — утверждение источника experience — событие работы персонажа thought — интерпретация preference — устойчивый вкус
activedisputedsupersededretracted

Сущности (entity.go:15) — идентификаторы предметов памяти:

persontopicplaceobjecteventproject

Роли связей memory_links (item.go:28):

subjectparticipantplacecontext

Источники (source.go:17):

journal_eventweb_documentruntime_actionpersona_version

Статус меняется только через Supersede (item.go:255): новая запись + старая становится superseded; cross-scope запрещён (ErrSupersedeScope). Тихой перезаписи нет.

Видимость: фильтр до выдачи — item.go:166 · scope.go:91

// аудитория = 'internal' → видно всё (scope_id = аудитория OR 'public') AND provenance существует и валиден AND каждый scope provenance ∈ public | internal | chat:<id> AND (provenance содержит 'public' OR саму аудиторию)

Условие живёт в SQL (visCond) и дословно дублируется предикатом ItemVisible в Go. Битый provenance → запись видна только internal. Имена и алиасы сущностей тоже имеют свой scope — алиас чужого скоупа не открывает даже публичную сущность.

Запись после хода — apply.go

  • До 5 memory-кандидатов (maxMemories=5): Items.Insert идемпотентно пишет запись + memory_sources + memory_links + memory_derivations; runtime сам назначает источник journal_event ref turn:<id> и provenance скоупа хода.
  • До 2 намерений (maxIntentions=2): ключ дедупа — JSON [kind, lower(topic), chatID], ON CONFLICT DO NOTHING; not_before = now + delay_hours, TTL 72 ч. defer дополнительно создаёт reply_later с темой = последний текст пачки (≤80 рун).
  • Salience — модель предлагает (по умолчанию 0.5), валидируется 0..1.

Retrieval: три инструмента хода — tools.go:27

memory_find_entities memory_entity_card memory_search

Скоуп чата внедряется зависимостью memory_scope — модель не выбирает аудиторию сама. Таймаут инструмента 30 с.

  1. Лексический канал: to_tsvector('russian', text), слова запроса через OR; только status='active'; ранжирование ts_rank → salience → свежесть.
  2. Семантический канал (если задан EMBEDDING_*): pgvector, embedding <=> $2::vector — косинусная близость, строка привязана к модели эмбеддингов (memory_embeddings.model).
  3. Слияние: каждый канал отдаёт пул 3×лимит, дубли убираются, затем жадное «разнообразие источников» (diverseOrder, первый элемент не сдвигается).
  4. Карточка сущности: сама сущность + до 10 записей (пул 30) с цитатами источников (kind + ref); сам provenance модели не показывается.

Лимиты: поиск по умолчанию 10, максимум 50; вызовы за ход — MODEL_TOOL_CALLS_LIMIT=5. На прямом вопросе первый вызов memory_search принудительный (tool_choice, только попытка 1 — на retry сбрасывается из-за thinking-режима).

Настроение и отношения — mood.go · relationships.go

Mood {valence −1..1, arousal 0..1, socialEnergy 0..1} хранится в character_state (строка CHECK (id=1)). При каждом чтении затухает к baseline персоны (файл config/persona.md, у Дио: 0.1 / 0.7 / 0.9):

current = baseline + (stored − baseline) · e^(−λ·часы)   λ = 0.5/ч → полураспад ≈ 1.4 ч

Дельты от модели сжимаются до ±0.3 за ход (MaxMoodDeltaPerTurn) и требуют основания (reason ≤500 рун). Текстовое описание строится порогами (DescribeMood: |Δvalence| > 0.4 — сильно, > 0.12 — слегка, и т.д.).

Отношения {familiarity, affinity, trust} по паре (сущность-человек, скоуп чата), SELECT … FOR UPDATE. За ход: affinity ±0.1, trust ±0.1; familiarity растёт только от runtime — +0.05 за каждый применённый значимый ход, модель им не управляет. Стартовое доверие 0.2.

Stances — текущее отношение — stance.go:82

Уникальны по (entity, aspect, scope). Обновление = revision + 1; основания в stance_basis только дополняются — прошлые аргументы не стираются. Поэтому возможны противоречивые аспекты одной сущности: «атмосфера праздника нравится, шум — нет». Против сущности по незнакомому имени — запись просто пропускается (повторный прогон того же summary — no-op).

04 · event_streams · internal/runtime

Журнал и восстановление

Каждый ход — запуск агента ago; его траектория записывается в event_streams. Восстановление после любого сбоя — это чтение журнала, никаких ручных флагов.

События хода — events.go:22 · journal.go:21

turn_started→ tool_call⇄tool_result×0..N → model_output→ deltas_applied+delivery_queued  ·  ветка:turn_skipped

Фоновые задачи пишут в свои потоки (stream = bg:intention:N, bg:consolidate:<chat>:<last>) WAL-события task_step_intended task_step_done с шагами collect / generate / apply. deltas_applied + delivery_queued пишутся внутри транзакции применения (SetHistoryTx) — либо всё, либо ничего.

Контракт адаптера журнала — runtime/journal.go

  • SetHistory блокирует все строки потока FOR UPDATE, требует непрерывности seq, сверяет префикс по jsonb-семантике и вставляет только суффикс. Сокращение истории → ErrHistoryConflict; уникальность 23505 (гонка писателей) — тоже.
  • DropHistory всегда запрещён (ErrDropForbidden) — журнал append-only.
  • ErrHistoryConflict при применении трактуется как «ход уже применён» (turn.go:349).
  • Тип события обязан совпадать с @type payload'а (ErrTypeMismatch).

Singleton — runtime/singleton.go

pg_try_advisory_lock(0x64696f) — «dio» в hex

Отдельное постоянное соединение; занято — процесс не стартует. Часы каждые 5 с: соединение потеряно → OnLost → процесс завершается (systemd перезапустит). Продолжать без singleton-защиты нельзя.

Бюджеты — runtime/budget.go

Перед каждым вызовом модели — Reserve: одна транзакция проверяет budget_counters (пул + текущий день), вставляет резерв с UNIQUE(operation_id) (retry той же операции — бесплатно). После сбоя пишется {"calls":1,"unknown":true} — неизвестная стоимость не считается нулём. Пулы: conversation и background; maintenance объявлен, но пока никем не используется.

05 · delivery_outbox · internal/telegram

Доставка: состояния и честные гарантии

Отдельный цикл каждые 500 мс забирает батч из 10 строк FOR UPDATE SKIP LOCKED в порядке чат → turn → position. exactly-once не заявляется: выбрана сторона «без дублей».

Жизненный цикл строки outbox

pending→ sending→ sent  ·  sending→retry_wait→ (not_before) →pending
sending→unknown · timeout / обрыв / crash / висит >1 мин
sending→failed · постоянная ошибка  ·  cancelled · чат ушёл вперёд / зависимые от unknown

Классификация ошибок отправки — delivery.go:253

СитуацияИсход
HTTP 429 (rate limit)retry_wait на RetryAfter от Telegram (запасной вариант — 1 с)
HTTP 5xxretry_wait с backoff 2 с · 2ⁿ⁻¹; после 5 попыток — failed
прочие 4xxfailed сразу
таймаут / connection reset / потеря ответаunknown — автоматически не повторяется; зависимые пузыри отменяются
  • Устаревание: перед отправкой проверяется, нет ли в чате новых pending-событий; есть — хвост пачки отменяется («чат ушёл вперёд — пузыри устарели»), но первый пузырь уходит всегда.
  • Темп: между пузырями пауза BubbleGap = 800 мс (в памяти, чистится через 10 мин). Реакция — SetMessageReaction списком ReactionType, цель — message_id первого события пачки.
  • Typing идёт всё время хода: SendChatAction("typing") сразу и каждые 4 с (TypingPulse).
  • История разговора берёт только status='sent' из outbox — неотправленный текст не изображается состоявшимся.
06 · internal/background

Фоновая жизнь

Один планировщик обслуживает намерения, консолидацию и cleanup. Все модельные задачи выполняются последовательно внутри тика — параллельной когниции нет. Пока в очереди есть прямые ходы, весь тик возвращается сразу: «фон отложен (§5.2)».

Тик планировщика — scheduler.go:225

  1. ResetRunning — зависшие running-намерения мёртвого процесса → pending
  2. Наблюдаемость: статистика очереди; варн роста после 3 подряд растущих тиков; варн исчерпания бюджета — раз в сутки
  3. ExpireOverdue: просроченные pending → cancelled, «срок истёк»
  4. Гейт прямой очереди: есть created-ходы с событиями? → тик заканчивается
  5. Намерения: ClaimDue ≤3 (FOR UPDATE SKIP LOCKED, порядок priority DESC, not_before, id) → исполнение; ошибка → пауза 15 мин; бюджет исчерпан → следующий UTC-полночь +5 мин
  6. Консолидация: ≤2 готовых эпизодов за тик (если не в cooldown)

Интервал тика — равномерный джиттер на [15 c, 30 c]. Никаких cron и внешних очередей.

Гейты намерения перед генерацией — executor.go:405

  1. expiresAt истёк → cancelled
  2. Дубль: то же kind + чат + lower(topic) в pending/running → cancelled
  3. Только личка — инициативы в группы выключены
  4. Лимиты инициативы: ≤2/сутки на чат, ≥4 ч между (считаются по доставленным инициативам)
  5. Лимит explore: ≤2 исследований в сутки
  6. Окно тишины 30 мин (ChatMoved): в чате были события или отправки — «инициатива неуместна»; explore освобождён

Инициатива создаёт строку в turns до генерации; промпт получает добавку «Ты сам решил написать первым…». После explore может создаваться share-намерение с задержкой 10 мин.

Исполнение фоновой задачи — executor.go

  • Задача = шаги collect → generate → apply; перед каждым шагом в WAL пишется task_step_intended, после — task_step_done. Чекпоинт {Attempt, TurnID} в task_checkpoints.
  • Номер попытки инкрементируется и чекпоинтится до вызова модели; retry того же шага переиспользует operation_id — бюджет не платит дважды.
  • Потолок генерации — 5 попыток (maxGenerateAttempts). Намерение при потолке: turn → skipped, намерение → failed, WAL помечает generate failed.
  • Если посреди задачи в очереди появились прямые ходы — errDeferred: намерение возвращается в pending, задача отменяется без штрафа.
  • Результат explore живёт только в WAL (turn-строки нет); при успехе — записи памяти с источником runtime_action ref intention:<id>.

Консолидация — episodes.go · consolidation.go

Эпизод готов при тишине 4 ч (личка) / 1 ч (группа) или при 100 событиях в сегменте. Агент "dio-consolidate" получает ≤30 записей эпизода (тексты ≤300 рун) и предлагает summary + ревизии stances:

  • Одна summary-запись: kind experience, salience 0.3, источник runtime_action ref episode:<chat>:<lastEvent>. Отдельной таблицы summaries нет — это обычная memory_items.
  • События эпизода получают summarized_at = now() — повторное применение эпизода невозможно.
  • Stances: Upsert с revision+1; максимум 5 аспектов по 100 рун.

⚡ Инцидент 2026-10-31: как фон выжег дневной пул

Консолидация падала HTTP 400 MissingSessionID — при клонировании конфига для фонового пути терялся session_id — и повторялась каждым тиком: ~1000 вызовов в пустоту за день, вся фоновая жизнь встала до полуночи.

  • Фикс причины: заголовок x-opencode-session теперь на всех путях (прямой ход, инициатива, explore, консолидация); групповые чаты (отрицательные id) тоже — прежний гард «≤ 0» их отсекал.
  • Усилитель (класс дефекта): потолок 5 попыток генерации + cooldown 24 ч для консолидации в runtime_state; после срока — свежий цикл попыток (WAL generate не помечен, Attempt сброшен).

Где код расходится со спекой v0.7

Страница построена по коду, поэтому эти отличия зафиксированы как есть — пригодится при следующей сверке спеки с реализацией.

  • Решения хода: в коде answer | react | ignore | defer — спека §11.2 описывала speak.
  • Забывания нет: salience — только ключ ранжирования; кода, понижающего её со временем, не существует (спека §10.5).
  • Семантическая индексация не подключена: IndexPending вызывается только из тестов — в проде поиск FTS-only, пока векторизация не встроена в цикл.
  • Quiet hours отсутствуют — из ночных пауз в коде только окно тишины 30 мин и дневные лимиты инициатив (спека §14.3 предполагала timezone-тишину).
  • maintenance-пул бюджетов объявлен, но не используется; дневной лимит вызовов общий для разговоров и фона.
  • turns.validated_result — колонка существует, код не пишет и не читает её (результат хранится событием model_output).
