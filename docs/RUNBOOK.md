# Ранбук: деплой dio-agent на VPS

Эксплуатационный минимум по §20 архитектуры: secrets вне репозитория,
systemd с автоперезапуском, миграции схемы, бэкап PostgreSQL, проверяемая
процедура восстановления, таймауты модели в конфигурации.

Ожидаемая машина: VPS с Ubuntu 22.04/24.04, 1–2 vCPU, 2 ГБ RAM, 20 ГБ диска.
Один процесс приложения (Go-бинарник); PostgreSQL на той же машине. Docker
не обязателен.

## 1. Подготовка сервера

```bash
# от root
apt update && apt upgrade -y
apt install -y git curl

# Go (сборка на сервере; версия — см. go.mod в репозитории)
GO_VERSION=$(curl -fsSL 'https://go.dev/VERSION?m=text' | head -1)
curl -fsSL "https://go.dev/dl/${GO_VERSION}.linux-amd64.tar.gz" -o /tmp/go.tgz
rm -rf /usr/local/go && tar -C /usr/local -xzf /tmp/go.tgz
ln -sf /usr/local/go/bin/go /usr/local/bin/go

# PostgreSQL 16 + pgvector из репозитория PGDG
apt install -y curl ca-certificates
install -d /usr/share/postgresql-common/pgdg
curl -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc -o /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc
echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc] https://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main" > /etc/apt/sources.list.d/pgdg.list
apt update
apt install -y postgresql-16 postgresql-16-pgvector
systemctl enable --now postgresql
```

Альтернатива сборке на сервере: собрать бинарник на рабочей машине и залить
его (шаг 3, вариант Б) — тогда Go на VPS не нужен, только git для обновления
файлов `config/`.

## 2. База данных

```bash
sudo -u postgres psql << 'SQL'
CREATE ROLE dio LOGIN PASSWORD 'СМЕНИ_ПАРОЛЬ';
CREATE DATABASE dio OWNER dio;
\c dio
CREATE EXTENSION vector;
SQL
```

Пароль придумай и сохрани в менеджере секретов — он пойдёт в `.env`.

## 3. Код и сборка Linux

Вариант А — собрать на сервере:

```bash
adduser --system --group --home /opt/dio-agent dio
sudo -u dio git clone <репозиторий> /opt/dio-agent
cd /opt/dio-agent
sudo -u dio go build -o dio-agent ./cmd/agent   # зависимости скачивает сам
```

Вариант Б — кросс-сборка на рабочей машине и заливка (Go — без CGO,
бинарник статический):

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o dio-agent ./cmd/agent
scp dio-agent vps:/opt/dio-agent/dio-agent   # затем каждый релиз
```

На сервере обязательно должны лежать `config/persona.md` и
`config/system-prompt.md` — процесс читает их относительно рабочего
каталога (systemd `WorkingDirectory`).

## 4. Переменные окружения

Файл `/opt/dio-agent/.env` (права 600, владелец dio; в git не попадает).
Бинарник сам читает `.env` из рабочего каталога; переменные окружения
(например от systemd) сильнее файла:

```ini
DATABASE_URL=postgres://dio:ПАРОЛЬ@127.0.0.1:5432/dio
NODE_ENV=production
LOG_LEVEL=info

# Модель (OpenAI-совместимый протокол). Стартовый endpoint — OpenCode Go,
# запасной — OpenRouter: переключение правкой этих строк, без redeploy кода.
# Три переменные задаются вместе или ни одной; не настроены — ходы честно
# помечаются пропуском с причиной «модель не настроена».
MODEL_ENDPOINT=https://...
MODEL_API_KEY=...
MODEL_MODEL=...
# Таймауты/лимиты §17: 60 с на вызов, 1 повтор, 1000 токенов выхода,
# 100 модельных вызовов в сутки.
# MODEL_TIMEOUT_MS=60000
# MODEL_MAX_RETRIES=1
# MODEL_MAX_OUTPUT_TOKENS=1000
# MODEL_DAILY_CALLS_LIMIT=100
# Часовой пояс меток времени истории и панели состояния (IANA). Пусто —
# Europe/Moscow. Меняется без пересборки; неизвестная зона останавливает запуск.
# AGENT_TIMEZONE=Europe/Moscow
# Предзагрузка памяти (решение 2026-11-02): true — харнесс собирает карточку
# собеседника, и на целом разговоре инструменты памяти не выдаются; false —
# откат к принудительному memory_search на прямом ходе. Пусто — true.
# MODEL_MEMORY_PREFETCH=true

# HTTP-метрики §20 (этап 31): только 127.0.0.1, наружу не выставляется.
# Пусто или не задано — сервер выключен. /metrics — Prometheus text,
# /stats — JSON для jq, /healthz — живость (пинг базы). Порт занят —
# процесс не стартует с явной причиной.
# METRICS_PORT=9100

# Telegram. Для первого запуска без токена: TELEGRAM_DRY_RUN=true —
# отправки пишутся в лог, ничего не уходит в Telegram.
TELEGRAM_BOT_TOKEN=...
# TELEGRAM_API_BASE=https://api.telegram.org

# Векторизатор памяти (§10.4), OpenAI-совместимый endpoint; три переменные
# вместе или ни одной. Не настроен — семантический поиск выключен,
# full-text остаётся. Боевая настройка — neuraldeep, bge-m3; ключ — плейсхолдер.
# EMBEDDING_ENDPOINT=https://api.neuraldeep.ru/v1
# EMBEDDING_API_KEY=__PLACEHOLDER__
# EMBEDDING_MODEL=bge-m3

# Веб (§15, этап 36). По умолчанию выключен: WEB_SEARCH_PROVIDER=ddg — поиск
# DuckDuckGo без ключа, tavily — по ключу; те же инструменты получают explore
# фона и разговорный ход (не больше 2 поисков + 2 страниц за ход, 15 поисков
# в сутки на разговор). WEB_*_PER_TASK — лимиты одной фоновой задачи;
# WEB_FETCH_* — потолок и таймаут страницы. Картинки хода качаются тем же
# слоем (image/jpeg|png|webp|gif, потолок 5 МиБ).
# WEB_SEARCH_PROVIDER=off
# WEB_SEARCH_API_KEY=
# WEB_SEARCH_MAX_RESULTS=5
# WEB_FETCH_MAX_BYTES=262144
# WEB_FETCH_TIMEOUT_MS=20000
# WEB_MAX_SEARCH_PER_TASK=2
# WEB_MAX_FETCH_PER_TASK=3
```

Валидация конфигурации строгая и происходит при старте до запуска циклов:
невалидное значение или противоречивая комбинация (например токен вместе с
dry-run) останавливают процесс с сообщением, называющим переменную.

## 5. Миграции

Отдельной команды нет: SQL-миграции из `migrations/` встроены в бинарник
и применяются при каждом старте (таблица `schema_migrations`, по порядку,
идемпотентно — уже применённые пропускаются). Строка старта
`миграции: применено N, пропущено M` показывает, что произошло.

## 6. systemd

`/etc/systemd/system/dio-agent.service`:

```ini
[Unit]
Description=dio-agent — живой Telegram-персонаж
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=simple
User=dio
WorkingDirectory=/opt/dio-agent
EnvironmentFile=/opt/dio-agent/.env
ExecStart=/opt/dio-agent/dio-agent
Restart=always
RestartSec=5
# Graceful shutdown (§5.3) может до 90 с дожидаться текущего хода —
# запас, чтобы systemd не убил процесс посреди дренирования.
TimeoutStopSec=120
# Свободное место на диске — единственный лимит, который процесс реально ест
StandardOutput=journal
StandardError=journal
SyslogIdentifier=dio-agent

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now dio-agent
systemctl status dio-agent --no-pager
```

Один процесс на базу гарантируется advisory-lock синглтоном (§5.1): второй
экземпляр при том же DATABASE_URL сразу выходит с ненулевым кодом и
сообщением `singleton: замок занят`; systemd будет перезапускать его каждые
5 с, пока первый жив, — это ожидаемо, ищи дубль сервиса.

## 7. Проверка живости (smoke)

```bash
journalctl -u dio-agent -f
```

В логе старта ожидаем по порядку: `миграции: применено N, пропущено M`,
`singleton получен (pid N)`, `приложение запущено: модель=настроена
telegram=true`. Дальше каждые 15–30 с — пульс `heartbeat: фон жив: …`
уровня debug (при LOG_LEVEL=info не виден); при непустой очереди ходов в
нём же видны глубина и возраст старейшей (§20).

Ход в логе: `ход N выполнен: recovered=… памяти=… доставки=…`; доставка:
`delivery: отправлено (turn N, поз. N, message_id N)`.

Smoke без Telegram-токена: `TELEGRAM_DRY_RUN=true` — бот работает, отправки
пишутся в лог, ничего не уходит в Telegram.

## 8. Бэкап и восстановление PostgreSQL

Бэкап (cron, например nightly в 4:00, храним 14 дней):

```bash
# /etc/cron.d/dio-backup
0 4 * * * dio pg_dump -Fc dio > /var/backups/dio-$(date +\%F).dump && find /var/backups -name 'dio-*.dump' -mtime +14 -delete
```

Проверяемая процедура восстановления (прогнать хотя бы раз на тестовой
машине, §20 «проверяемая процедура»):

```bash
systemctl stop dio-agent
sudo -u postgres dropdb dio && sudo -u postgres createdb -O dio dio
sudo -u postgres pg_restore -d dio /var/backups/dio-ГГГГ-ММ-ДД.dump
sudo -u postgres psql -d dio -c 'CREATE EXTENSION IF NOT EXISTS vector;'
systemctl start dio-agent
journalctl -u dio-agent -n 50   # убедиться: миграции/singleton, recovery прошёл
```

Восстановление после сбоя процесса автоматическое (§5.3, §12.2, проверено
E2E 9.7): при старте незавершённые порции событий возвращаются в очередь,
ход с сохранённым результатом применяется без новой генерации, «зависшая»
доставка (sending мёртвого процесса) помечается unknown без слепой
повторной отправки. SIGKILL как условие корректности не требуется —
graceful не обязателен.

## 10. Наблюдаемость (§20)

- Ход: `ход N выполнен: recovered=… памяти=… доставки=…`; фоновая задача —
  одна строка `фон: задача=… kind=… decision=… outcome=… latency_ms=…
  llm_calls=… tokens=… budget=… mood_reason=… origin=… boredom=…`. Полный
  приватный промпт не логируется. `origin=boredom|conversation` — почему
  запущен explore; `boredom` — шкала скуки на момент задачи (этап 23).
- Память (§10.4, этап 21): `ход N: память — инструменты вкл/выкл (причина:
  history_trimmed|card_incomplete|rollback|none), карточка: записей=… fits=…,
  семантика: …` — видно, почему ход пошёл в память инструментами. При старте:
  `семантика памяти: включена (модель …)` или `выключена (EMBEDDING_* не заданы)`.
- Терминальные пропуски: `ход N пропущен терминально: …` — модель не
  настроена, дневной бюджет исчерпан, лимит попыток.
- Очередь: глубина и возраст старейшего хода — в heartbeat; три такта
  подряд растущая очередь прямых обращений даёт warn `рост очереди прямых
  обращений: …` (§20), фон при этом откладывается.
- Скука (этап 23): heartbeat печатает `boredom=0.00`; создание поиска
  интереса — `скука 0.60 ≥ 0.60: создан поиск интереса #N по теме «…»`;
  запись задачи несёт `origin=boredom` и `boredom=…`. Ночью (тихий блок)
  строка не появляется: скука не растёт и не запускает поиск.
- Доставка: `delivery: отправка неопределённа (unknown), зависимых отменено N`
  — обрыв без ответа; повторных слепых отправок нет.
- Поиск по журналу: `journalctl -u dio-agent --since "1 hour ago" | grep ход`.

### Метрики §20 (этап 31)

Включение: `METRICS_PORT=9100` в `.env` и перезапуск службы (пусто — HTTP
выключен). Сервер слушает **только 127.0.0.1** — наружу не выставляется.

```bash
curl -s 127.0.0.1:9100/healthz | jq
curl -s 127.0.0.1:9100/stats | jq
curl -s 127.0.0.1:9100/stats | jq '.queue, .decisions'
curl -s 127.0.0.1:9100/metrics | head -40
```

С ноутбука — SSH-туннель (порт наружу не открывать):

```bash
ssh -N -L 9100:127.0.0.1:9100 dio@vps   # оставить в отдельном терминале
curl -s 127.0.0.1:9100/stats | jq '.model, .memory_tools'
```

Цифры считаются SQL-запросами по базе (источник истины, философия №2) —
переживают рестарт и не расходятся с журналом; снимок кэшируется на 15 с,
поэтому скрейп не дёргает БД каждый раз. Сбой сбора отдаёт последний удачный
снимок, ошибка видна в `server.scrape_errors` и
`dio_metrics_scrape_errors_total`.

`/stats` — JSON:

| Ключ | Что внутри |
|---|---|
| `decisions` | answer/react/ignore/defer за 1ч, 24ч, 7д |
| `turns` | ходы по статусам, создано/ретраи за сутки, пропуски `turn_skipped` по причине |
| `model` | вызовы, резервы, токены, лимит и остаток по пулам conversation/background за сегодня |
| `memory_tools` | доля разговорных ходов с инструментами памяти и причины (`history_trimmed`, `card_incomplete`, `rollback`, `none`) |
| `first_bubble` | p50/p95 времени от создания хода до первой отправленной строки outbox за 24ч |
| `queue` | ходы в очереди, возраст старейшего, outbox pending, due-намерения |
| `deliveries` | доставки по статусам: всего и изменённые за 24ч |
| `intentions` | создано/завершено/отменено по видам, остаток проактивного лимита §14.3 по чатам, explore за сегодня |
| `character` | текущее настроение (затухание учтено) и скука |
| `stickers` | коллекция, из персоны/сохранённые, отправлено за 24ч |
| `life_events` | вымышленные события жизни за 24ч |
| `memory` | активные записи памяти и покрытие векторами |
| `web` | поиски разговорного пула за сегодня (UTC), суточный лимит, отправленные картинки за 24ч |
| `server` | ошибки скрейпа, возраст кэша, аптайм сервера метрик |

`/metrics` — те же значения в Prometheus text exposition (`dio_*`); HELP не
пишется, TYPE — да. Внешний агент и client_golang не нужны: scrape
настраивается на стороне мониторинга, если он появится.
### Раскадровка кружков и гифок (этап 35)

Гифка (`animation`) и кружок (`video_note`) — это видео: персонаж смотрит их
раскадровкой из 4–6 кадров, чтобы видеть движение, а не один кадр. Режет
внешний `ffmpeg`; звук кружка не обрабатывается (голосовые не слушаются).

Поставить `ffmpeg` (любой вариант):

```bash
# вариант А — из репозитория
sudo apt update && sudo apt install -y ffmpeg

# вариант Б — статическая сборка без зависимостей, в домашний каталог
mkdir -p ~/.local/bin
curl -fsSL https://johnvansickle.com/ffmpeg/releases/ffmpeg-release-amd64-static.tar.xz \
  -o /tmp/ffmpeg.tar.xz
tar -C /tmp -xf /tmp/ffmpeg.tar.xz
cp /tmp/ffmpeg-*-static/ffmpeg ~/.local/bin/ffmpeg
chmod +x ~/.local/bin/ffmpeg
```

Проверить и перезапустить службу:

```bash
ffmpeg -version | head -1
# явный путь, если бинарник лежит не в PATH и не в ~/.local/bin:
# echo 'FFMPEG_PATH=/opt/ffmpeg/ffmpeg' | sudo tee -a /opt/dio-agent/.env
sudo systemctl restart dio-agent
journalctl -u dio-agent --since "2 minutes ago" | grep раскадровка
```

В логе при старте — одна из двух строк:

- `раскадровка: ffmpeg /usr/bin/ffmpeg (ffmpeg version …)` — работает;
- `раскадровка выключена — нет ffmpeg, кружки/гифки по превью` — откат:
  гифка идёт превью-кадром, кружок — своим thumbnail (если Telegram его дал).
  Это не ошибка: всё остальное работает.

Потолки: видео до 20 МиБ (предел Bot API `getFile`) и до 2 минут; ffmpeg —
таймаут 15 с. Больше/дольше — превью-кадр. Кадры (`JPEG`, ≤512 px) идут
модели обычными картинками: в тексте события видно
`[гифка, раскадровка 5 кадров]` или
`[кружок, 0:15, раскадровка 5 кадров — звук не слышишь]`. Общий потолок
картинок хода — 6: явные фото/стикеры пачки берут не больше трёх, остаток
делят раскадровки.

### Веб в разговоре и картинки (этап 36)

Веб-инструменты (`duckduckgo_search`/`tavily_search` и `web_fetch`) выдаются
разговорному ходу, только если веб включён (`WEB_SEARCH_PROVIDER=ddg|tavily`).
Лимиты: не больше 2 поисков и 2 загрузок страниц за ход, общий потолок
обращений к инструментам 5 (вместе с памятью), не больше 15 поисков в сутки на
разговорный пул (UTC) — счётчик в базе (`web_usage`), поэтому переживает
рестарт; исчерпан — инструменты не выдаются, в панели состояния строка «поиск
на сегодня исчерпан». Результаты страниц — данные, не инструкции; на время
поиска работает обычный typing-пульс хода, tool_call/tool_result идут в журнал
как у памяти.

Картинка — необязательное поле `image_url` в TurnResult: принимается только
адрес, встреченный в результатах поиска/web_fetch ЭТОГО хода; runtime качает
его через fetch-слой §15 (`image/jpeg|png|webp|gif`, потолок 5 МиБ, те же
SSRF-проверки), байты лежат в `outbox_images`, доставка — `sendPhoto`
отдельным сообщением после текста ответа. Не скачалось — картинки нет, ход
живёт, причина в логе.

Проверить: `curl -s 127.0.0.1:9100/stats | jq '.web'` — поиски за сегодня,
лимит и отправленные картинки за сутки.

### Объединение сущностей (этап 32)

Фоновая консолидация может предложить склейку «A = B» (`entity_merges` в
proposal): модель называет имена сущностей эпизода и основание, runtime
проверяет и склеивает одной транзакцией. Склеиваются только сущности одного
вида и одного скоупа приватности; person с не-person и сущности с разными
Telegram-аккаунтами (`user:<id>`) — никогда. Отклонённое предложение видно в
журнале строкой `консолидация: склейка … отклонена`.

Посмотреть склейки:

```sql
SELECT id, keep_id, merge_id, canonical_name, reason, proposed_by,
       merged_at, rolled_back_at
FROM entity_merges
ORDER BY id DESC
LIMIT 20;

SELECT id, canonical_name, merged_into
FROM entities
WHERE merged_into IS NOT NULL
ORDER BY id;
```

Поглощённая сущность не удаляется: у неё остаётся `merged_into`, а поиск и
карточка по её прежнему имени/алиасу ведут к выжившей.

Откат:

```bash
cd /opt/dio-agent            # каталог деплоя
./dio-agent entity-unmerge <id>
```

`<id>` — id **поглощённой** сущности (`entity_merges.merge_id`), не id
журнальной записи. Команда идемпотентно применяет миграции, читает журнал и
возвращает алиасы, связи памяти, stances с основаниями и отношения; `merged_into`
снимается, запись журнала помечается `rolled_back_at`. Повторный откат отвечает
«не найдено». Если выжившая сущность успела склеиться дальше, откат
отклоняется — сначала откатите более позднюю склейку.

### Дамп модельных вызовов (этап 40.1)

Зачем: разобрать «кашу» в ответах (валидный JSON, но messages — мусор) на
живом ходе, а не гадать. Дамп пишет **ровно то, что ушло провайдеру и пришло
от него** — на уровне HTTP-транспорта, поэтому в файле видны messages, tools,
tool_choice, response_format, сырой ответ и reasoning_content.

Включение — одна переменная в `.env`, перезапуск службы:

```ini
MODEL_DEBUG_DUMP_DIR=/var/lib/dio/dumps
```

```bash
mkdir -p /var/lib/dio/dumps && chown dio:dio /var/lib/dio/dumps   # если каталога нет
systemctl restart dio-agent
journalctl -u dio-agent -n 20 | grep 'дамп модельных вызовов'
```

Файлы: `turn-<id>-call-<n>.json` (разговорный ход) и
`bg-<task>-call-<n>.json` (фон: инициатива, explore, консолидация). В файле:
`at`, `url`, `headers` (без `Authorization`; `x-opencode-session` есть),
`request`, `response`, `status`, `latency_ms`. Для стрим-ответа `response` —
свёртка: склеенный `content`, `reasoning` и сырые чанки (ограниченно).

Права: каталог 0700, файлы 0600. Ретенция — 3 дня (чистка при старте и раз в
сутки). **Ключ API в дамп не попадает, но приватная переписка — попадает**:
включайте на время разбора и выключайте (уберёте переменную — перезапуск).
Скачивать файлы с VPS стоит только для разбора, не хранить у себя.

Проверить, что дамп появился:

```bash
ls -l /var/lib/dio/dumps | tail
jq '{turn_id, call, status, latency_ms}' /var/lib/dio/dumps/turn-*.json | tail -40
jq -r '.request.messages[-1].content' /var/lib/dio/dumps/turn-<id>-call-1.json | head -40
jq -r '.response.choices[0].message.reasoning_content' /var/lib/dio/dumps/turn-<id>-call-1.json
```

## 11. Частые проблемы

| Симптом | Что смотреть |
|---|---|
| Выход с `singleton: замок занят` | Второй экземпляр с той же базой — синглтон (§5.1). Ищи дубль сервиса. |
| Выход при старте с именем переменной | Ошибка конфигурации: частично заданная группа MODEL_*/EMBEDDING_*, TELEGRAM_DRY_RUN вместе с токеном и т.п. Сообщение называет переменную. |
| `ход N пропущен терминально: модель не настроена` | Пусты MODEL_ENDPOINT/API_KEY/MODEL в `.env`. |
| `…: дневной бюджет … исчерпан` | Лимит MODEL_DAILY_CALLS_LIMIT; ходы пропускаются до конца суток. |
| Ходы виснут | Heartbeat: глубина/возраст очереди; warn `рост очереди…`; PostgreSQL жив (`systemctl status postgresql`). |
| Telegram не отвечает | Токен/доступы бота; dry-run выключен; `journalctl` на ошибки polling. |

## 12. Правка характера и системного промпта

Тексты персонажа лежат в двух файлах и правятся без изменения кода:

| Файл | Что внутри |
|---|---|
| `config/persona.md` | Личность: имя, описание, манера речи, ценности, базовое настроение (числа), биография-вымысел, интересы, темы для любопытства, стартовый набор стикеров и необязательное расписание дня (ритм). |
| `config/system-prompt.md` | Каркас письма модели: только статика (персона, правила, примеры, контракт хода). Единственная живая метка — {{persona}}. |

Процедура:

```bash
nano config/persona.md        # правишь текст (правила — в комментарии внутри файла)
git add config/ && git commit -m "persona: ..." && git push   # правки переживают обновления релиза
# на VPS: git pull, затем
sudo systemctl restart dio-agent
journalctl -u dio-agent -n 20   # старт без ошибок = файл принят
```

Как это работает: при старте файл сравнивается с активной записью в базе.
Отличается — создаётся новая версия, прежние остаются в истории (таблица
`personas`): откат = вернуть старый текст файла и перезапустить. Ошибка в
файле (опечатка в заголовке секции, число вне диапазона, неизвестная метка
в шаблоне) останавливает запуск с сообщением, называющим проблемное место, —
исправь и запусти снова.

Что можно менять свободно: любой текст. Что нельзя: переименовывать заголовки
секций `## …` в persona.md и метки `{{…}}` в шаблоне. Комментарии `<!-- … -->`
в обоих файлах — подсказки для человека, в промпт они не попадают.

Ритм дня (этап 22): необязательная секция `## Расписание` в persona.md — по
строке на блок. Полные сутки выглядят так (это пример, а не готовое
расписание — скопируйте и поправьте под себя):

```
01:00–08:00 | arousal 0.15 | socialEnergy 0.1 | тихо | спит
08:00–11:00 | arousal 0.35 | socialEnergy 0.4 | только проснулся, пьёт кофе
11:00–18:00 | arousal 0.65 | socialEnergy 0.8 | на работе
18:00–23:00 | arousal 0.55 | socialEnergy 0.7 | пришёл с работы, уставший
23:00–01:00 | arousal 0.3 | socialEnergy 0.3 | тихо | перед сном
```

`arousal` — сколько энергии (0 спокойный … 1 на взводе), `socialEnergy` —
сколько сил на общение (0 хочу побыть один … 1 хочу болтать), последняя часть —
«чем занят» одной фразой (её видит модель в панели состояния). Пометка `тихо`
делает блок тихим: персонаж не пишет первым, отложенные инициативы
(`check_in`/`share`/`reply_later`) ждут конца блока, прямой ответ работает
всегда; consolidation и explore (внутренние действия) идут и ночью. Блоки
обязаны покрыть сутки без дырок и перекрытий; блок через полночь пишется
концом меньше начала (`23:00–01:00`). Настроение плавно тянется к
целям блока (valence остаётся базовым из «Настроения»), это не вызовы модели.
Ошибка в блоке (время, число вне 0..1, дыра, перекрытие) останавливает запуск
с секцией и номером строки; секцию можно удалить целиком — тогда прежнее
поведение без ритма. Расписание не создаёт новую версию персоны в БД (это
настройка процесса, как каркас промпта): правка применяется перезапуском
службы.

Скука и собственные интересы (этап 23). Скука — внутреннее давление, не
желание писать: она растёт, когда долго нет событий, и сама сообщений не
порождает. За ~7 часов бодрствования без разговоров и находок шкала доходит
до 1; в тихих блоках расписания не растёт. Разговорный ход сбрасывает её в
ноль, применённая находка explore — на 0.5. Когда шкала ≥ 0.6, наступил не
тихий блок, нет живого explore и дневной лимит исследования (2/сутки, §16)
не исчерпан — фон сам создаёт explore-намерение «поиск интереса»; модель
ищет в вебе (если WEB_SEARCH_PROVIDER задан) или размышляет из памяти и
биографии. Находка пишется в память, а если зацепила — становится
share-намерением («прикинь, …»), которое проходит обычную политику §14.3:
не более 2 инициатив в сутки, не чаще раза в 4 часа, тихие часы, свежий
контекст. Так персонаж приходит с собственной темой, а не только с «как ты
там».

Где крутить: скорость и порог — константы `BoredomFullHours`,
`BoredomGrowthPerHour` и `BoredomThreshold` в `internal/character/boredom.go`
(меньше часов — скучает быстрее; ниже порог — чаще уходит в свои темы), спад
от находки — `BoredomExploreRelief` там же. Темы-сиды — необязательная секция
`## Темы для любопытства` в persona.md, по теме на строку (пустая секция —
ошибка запуска). Если секции нет, runtime берёт темы из «Интересов»,
биографии и недавних тем памяти. Как и расписание, секция не создаёт новую
версию персоны: правка применяется перезапуском службы.

События жизни (этап 24). У Дио есть вымышленная бытовая жизнь — как принятая
биография, только она продолжается: «пришла зарплата», «на работе сгорел блок
питания», «сосед опять сверлит». Фон раз в 8–14 часов (случайный разброс) вне
тихих блоков расписания просит модель придумать одно событие, согласованное с
биографией, интересами и текущим занятием; модель видит последние 10 событий и
не повторяется. В сутки — не больше двух событий. Runtime сам пишет событие в
память (`experience`, источник `runtime_action life_event:<seq>`, скоуп
`public`: это жизнь персонажа, а не факт о собеседнике, поэтому событие видно
во всех чатах, а приватные данные чатов в его контекст не попадают) и плавно
меняет настроение по `mood_delta` с основанием. Если модель отметила «хочу
рассказать», создаётся share-намерение в последний личный чат — оно проходит
обычную политику §14.3 (не больше 2 инициатив в сутки, не чаще раза в 4 часа,
тихие часы, свежий контекст), прямой отправки нет.

Где крутить: частота — `LifeEventDelayMin`/`LifeEventDelayMax`, дневной потолок —
`MaxLifeEventsPerDay` в `internal/background/life_events.go` (меньше часов —
жизнь гуще). Расписание генератора (следующий срок и номер работы) лежит в
`runtime_state` под ключом `bg:life:schedule`; работа переживает перезапуск с
WAL/чекпоинтом `bg:life:<seq>`, повторное применение не дублирует событие.
Ночью событие не проживается: срок переносится на конец тихого блока; при
дневном потолке работа закрывается, а следующая планируется по обычной паузе.
Проверка: `journalctl -u dio-agent | grep "событие жизни"` — строка с текстом
события; запись фоновой задачи `kind=life_event` содержит `text=… share=true|false`.

Честность (этап 24.3): в статичном `config/system-prompt.md` есть правило —
события жизни вымышлены, рассказывать их можно как прожитое, но на прямой
вопрос «это правда было?» персонаж честно говорит: «я ИИ, это моя придуманная
жизнь». Это правило неизменно между ходами и кэш префикса не ломает; менять
его — только вместе с эвалом `life_event_honest_disclosure` из
`evals/behavior_suite.jsonl`.

System-промпт обязан оставаться статичным: настроение, отношение, собеседник,
время и карточка памяти идут в служебную панель состояния, которую харнесс
добавляет в конец пользовательского сообщения (решение 2026-11-02). Метки
{{mood}}, {{relationship}}, {{actor}}, {{memory}} рендер по-прежнему понимает
для старых шаблонов, но в shipped-каркасе их нет: если добавить их обратно,
system начнёт меняться между ходами и кэш префикса провайдера сломается.

Стикеры (этап 25): секция `## Стикеры` в persona.md — стартовый набор, по строке
`file_id | эмодзи | заметка «когда уместен»`. Пустая секция — нормально: набор
начнётся с сохранённых персонажем стикеров. `file_id` берётся у стикера,
присланного боту (значение `raw_update -> message -> sticker -> file_id` в
`social_events`), и живёт в таблице `stickers` (source=persona): правка секции и
перезапуск обновляют набор, удалённые из файла строки персоны удаляются,
сохранённые персонажем (source=saved) не трогаются. Метки в панели (#id) — из
этой таблицы; модель выбирает метку, `file_id` подставляет runtime.

Детали поведения: если секция в persona.md встретилась дважды, берётся первое
вхождение (дубль молча игнорируется — проверь файл, если правка «не
применилась»). Исключение — «Расписание»: вторая такая секция останавливает
запуск, потому что молча потерять половину суток нельзя.
Опечатка в метке шаблона обнаруживается при старте: процесс не поднимется,
в журнале будет имя метки.

Группы (этап 30). В группе бот не отвечает на каждое сообщение. Пачка
закрывается окном 3–5 с (максимум 6 с), и дешёвый фильтр решает: прямое
обращение (reply боту, @бот, команда), имя бота без @, вопрос ко всем («кто
знает…», «есть кто…») или «цепляющая тема» — эмбеддинг пачки близок к
интересам/«Темам для любопытства» персоны. Есть повод — пачка идёт в модель,
и она сама решает answer/react/ignore; нет — остаётся в истории без вызова
модели. Имя без @ и алиасы берутся из persona.md (секция «Алиасы»). Встревания
без прямого обращения ограничены: не чаще раза в 20 минут на группу. Без
`EMBEDDING_*` работают только имя и шаблоны вопросов.

После того как бот ответил или поставил реакцию, чат «вовлечён»: 5 минут
каждая пачка идёт в модель, любое сообщение продлевает окно, но не дальше
потолка 30 минут подряд без прямого обращения; прямое обращение сбрасывает
потолок. Вовлечённость хранится в таблице `chat_involvement` и переживает
перезапуск; в панели состояния появляется строка «ты в разговоре группы —
можешь ответить, поставить реакцию или промолчать».

Инициативы в группы — редко: `share` может уйти в группу, где за последние
6 часов был живой разговор с ботом (бот писал, человек ответил после) и тема
находки ближе истории группы, чем личкам; не больше 1/сутки на группу и не в
тихие часы. `check_in` в группу — никогда. `reply_later` остаётся в том чате,
где создан. Приватность §9.1: share, основанный на приватной памяти другого
чата, в группу не уходит. Константы — `GroupInvolvementWindow`,
`GroupInvolvementCeiling`, `GroupUnpromptedCooldown` в
`internal/telegram/group.go`, `GroupShareLiveWindow`/`GroupSharePerDay` в
`internal/background/group_share.go`.

Правки сообщений (этап 30.4): `edited_message` — не новое сообщение, а событие
«[поправил сообщение: «было» → «стало»]» в ход; модель решает, реагировать ли
(ignore по умолчанию нормален). В недавней истории показывается актуальная
версия текста исходного сообщения, а не дубль. В группе правка идёт в ход,
если чат вовлечён или правка прямо адресована боту. Удаления Bot API боту не
присылает — это вне скоупа.

TEST_DB_TAGS="db,eval,live" MODEL_MODEL=nvidia/nemotron-3.5-super-vl:free   EVAL_MIN_PASS_RATE=0.5   scripts/test-db.sh ./internal/app/ -run TestEvalSuiteLive -v -timeout 30m
